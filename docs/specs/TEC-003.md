# TEC-003: Fixed-timestep sim loop (20 Hz); render interpolates between snapshots

GDD: docs/gdd/01-tech.md — "Fixed-timestep sim loop (20 Hz); render interpolates between snapshots."
Milestone: M0   Depends on: TEC-002 (merged)
Model: sonnet — the design is locked below; the risk is in two small pure functions, and both get tests.
Branch: tec-003-fixed-timestep

## Desired result
The sim advances exactly 20 ticks per real second on average, no matter how irregular the host's timer is. It never spirals when the tab was throttled. The renderer draws smoothly at display rate by interpolating between the last two snapshots, matching entities **by id** (order in the arrays is not stable).

## Locked design

1. `sim/src/fixed-step.ts` (pure, browser-free; usable by a future Node host):
   ```ts
   export const MAX_STEPS_PER_ADVANCE = 5;
   export interface StepClock { accumulatorMs: number }
   /** Adds elapsedMs, returns how many ticks to run now. If more than MAX_STEPS_PER_ADVANCE would be due, runs MAX and drops the remaining backlog (accumulator := 0): the world pauses rather than fast-forwards after throttling. */
   export function advance(clock: StepClock, elapsedMs: number): number
   ```
   Negative or non-finite elapsedMs → throw (an actionable error).
2. `client/src/sim-worker.ts`: replace the `setInterval(step, TICK_MS)` loop with a timer that fires roughly every `TICK_MS / 2`. On each fire, compute elapsed from `performance.now()` (the adapter is the only place wall-clock time is read), call `advance`, run that many `step()`s, and post **only the newest** snapshot when steps > 0. Error handling stays as it is.
3. `client/src/render/interpolate.ts` (pure):
   ```ts
   export interface Frame { count: number; ids: Uint32Array; x: Float32Array; y: Float32Array; kind: Uint16Array }
   export function interpolate(prev: Snapshot | null, curr: Snapshot, alpha: number, out: Frame): void
   ```
   - alpha is clamped to [0, 1].
   - For each entity in `curr`: if the same id exists in `prev`, lerp prev→curr; otherwise use the curr position (a new entity, no lerp). Entities only in `prev` are dropped.
   - `out` is reused frame-to-frame (grow its arrays only when count exceeds capacity) so there's no per-frame allocation in the steady state.
4. `client/src/render/snapshot-view.ts`: `update` takes a `Frame` instead of a `Snapshot` (a Snapshot is structurally a Frame plus `tick`, so either works).
5. `client/src/main.ts`: keep `prev`, `curr` and `currReceivedAt` (performance.now). In `app.ticker`, `alpha = (now - currReceivedAt) / TICK_MS`, then `interpolate(prev, curr, alpha, frame)` and `view.update(frame)`. Rendering is one tick behind, which is the standard trade for smoothness. When a snapshot arrives: `prev = curr; curr = new; currReceivedAt = now`.

## Acceptance criteria
- AC1 No drift — proven by: test "advance() over irregular elapsed times yields floor(total / TICK_MS) steps in total" (e.g. 1000 calls with seeded pseudo-random 1–40 ms values).
- AC2 No spiral — proven by: test "a 10 s gap yields MAX_STEPS_PER_ADVANCE steps and drops the backlog" (the next 50 ms call yields exactly 1).
- AC3 Matching by id — proven by: test "interpolate lerps by id when entity order differs between prev and curr", plus a new entity in curr that isn't lerped, plus alpha clamping.
- AC4 Real rate — proven by: build, preview on port 4179, then load the page for ~3 s with a temporary counter in main.ts (removed afterwards) → between 55 and 65 snapshots received. Report the number.
- AC5 Smooth and error-free — proven by: check.mjs → canvas true, errors []; movers visible in the screenshot.
- AC6 Green — `npm run check && npm test && npm run build` → exit 0.
