# TEC-004: ECS-style entity storage on typed arrays

GDD: docs/gdd/01-tech.md — "ECS-style entity storage on typed arrays."

Model: opus — because every sim system and the snapshot protocol (TEC-002) build on this data layout.

## Desired result
`sim/src/ecs.ts` gives the sim a small, deterministic struct-of-arrays entity store: entities are generational IDs, components are named typed-array columns, and iteration order depends only on the sequence of operations. Stale IDs and recycled slots can never leak old data.

## Locked design
Own implementation, no library. Rationale: ~150 lines; we need deterministic iteration and direct column access for zero-copy snapshots; JS ECS libraries have had breaking API churn (e.g. bitECS 0.3 → 0.4).

```ts
export type EntityId = number;           // u32: low 20 bits = slot index, high 12 bits = generation
export type ColumnType = "f32" | "f64" | "i32" | "u32" | "u16" | "u8";
export type Schema = Record<string, ColumnType>;
// Store<S>: for each key of S, the matching typed array (Float32Array for "f32", …), length = capacity
export interface Component<S extends Schema> { readonly id: number; readonly name: string; readonly store: Store<S> }

export class World {
  constructor(options?: { capacity?: number })   // default 16384; must be 1..2^20, else throw
  readonly capacity: number
  get count(): number                            // alive entities
  create(): EntityId                             // throws "World is full (capacity N)…" when full
  destroy(id: EntityId): void                    // throws if not alive; removes all components; bumps generation (12-bit wrap)
  isAlive(id: EntityId): boolean                 // false for stale or never-issued IDs
  indexOf(id: EntityId): number                  // slot index into component stores; throws if not alive
  register<S extends Schema>(name: string, schema: S): Component<S>   // throws on duplicate name
  add(id: EntityId, c: Component<Schema>): void      // zeroes that slot's columns for c
  remove(id: EntityId, c: Component<Schema>): void
  has(id: EntityId, c: Component<Schema>): boolean
  each(cs: readonly Component<Schema>[], fn: (id: EntityId, index: number) => void): void
}
```

Internals (locked):
- Alive set: dense `Uint32Array` of slot indices plus a sparse position array; swap-remove on destroy. `each` walks the dense array in order.
- Free slots: LIFO stack, so slot reuse is deterministic.
- Membership: one `Uint8Array(capacity)` "has" flag array per component.
- `generation: Uint16Array(capacity)`, masked to 12 bits. IDs are built with arithmetic (`gen * 2**20 + index`), not `<<`, so they never go negative.
- Creating or destroying entities inside `each` throws ("structural change during each()"); a guard flag is enough.
- No `any` in the public API.

## Acceptance criteria
- AC1 Generational IDs — proven by: test "destroyed id is not alive, even after its slot is reused".
- AC2 No stale data — proven by: test "a recycled slot reads zero for a newly added component".
- AC3 Queries are exact — proven by: test "each() visits exactly the entities that have all requested components, in deterministic order" (the same op sequence on two worlds gives identical visit lists).
- AC4 Misuse is loud — proven by: tests for capacity overflow (message includes the capacity) and structural change inside each().
- AC5 Browser-free and green — proven by: `npm run check && npm test && npm run build` → exit 0.

## Tests
`sim/src/ecs.test.ts` with exactly the AC1–AC4 cases. Each guards a bug that would otherwise corrupt state silently. Show each test fails when its guarded behaviour is broken (e.g. skip the zeroing in `add`), then revert.
