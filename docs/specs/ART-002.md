# ART-002: Palette system — biome palettes + global pop palette

GDD: docs/gdd/10-art-audio.md — "Palette system: biome palettes + global pop palette."
Milestone: M0   Depends on: ART-001 (merged)
Model: sonnet — data plus a small validated loader; the format is locked below.
Branch: art-002-palettes

## Desired result
Generators get their colors from named, validated palette files instead of hard-coded values. There's a global **pop** palette (hits, crits, rarity, magic elements, UI accents: always bright, readable in every biome) and a first biome palette, **meadow**. A broken palette file fails the build and tests with a message naming the file and key.

## Locked design
- Data: `tools/art/palettes/<name>.json`:
  ```
  { "name": "<name>",                    # must equal the file stem
    "ramps":  { "<ramp>": ["#rrggbb", ...] },   # 2–8 colors each, ordered dark → light by relative luminance
    "colors": { "<color>": "#rrggbb" } }        # optional single colors
  ```
  Keys match `[a-z0-9_]+`, hex is lowercase `#rrggbb`, and no other top-level keys are allowed.
- `tools/art/lib/palette.py`:
  - `Palette.ramp(name) -> list[tuple[int, int, int, int]]` (RGBA, alpha 255)
  - `Palette.color(name) -> tuple[int, int, int, int]`
  - `load_palette(name) -> Palette` and `load_all() -> dict[str, Palette]`
  - Every rule is validated on load: name/stem match, hex format, ramp length, dark→light order (WCAG relative luminance, strictly increasing), key format, unknown keys. Errors name the file and the key.
  - A missing ramp or color raises `KeyError` naming the palette and the key.
- `tools/art/lib/context.py`: add `Context.palette(name) -> Palette` (loads are cached per build).
- `build.py`: validate all palettes once at startup (`load_all()`), so a broken file fails the build even if no generator uses it yet.
- Shipped palettes:
  - `pop.json`: colors `hit_flash`, `crit`, `heal`, `xp`. Ramps `rarity_common`, `rarity_uncommon`, `rarity_rare`, `rarity_epic`, `rarity_legendary` (2–3 shades each). Ramps `fire`, `frost`, `stone`, `storm`, `life`, `shadow` (3–4 shades each).
  - `meadow.json`: ramps `grass`, `grass_dry`, `dirt`, `stone`, `water`, `wood`, `leaf`, `flower_warm`, `flower_cool` (3–6 shades each).
  - Art direction: saturated, cozy, lighthearted, Stardew-ish warmth. Pop colors must stand out against meadow greens.
- `gen/debug.py`: `debug/checker16` takes its two greens from `meadow.grass`, and the `debug/mover32` outline uses the darkest shade of its fill ramp or a pop color. The mover hue from `ctx.rng` stays.

Delegated micro-decisions: the actual color values, within the direction above.

## Acceptance criteria
- AC1 Palettes load and validate — proven by: test "all shipped palettes load".
- AC2 Bad data is loud — proven by: one parametrized test covering bad hex, an unsorted ramp, an unknown top-level key, a name/stem mismatch and a ramp that's too short, each raising with the file and key in the message.
- AC3 Generators use palettes — proven by: grep shows no hex color literals left in gen/debug.py, and `debug/checker16` pixels equal `meadow.grass` shades (one assert in an existing or new test).
- AC4 Still deterministic — proven by: two builds into temp dirs → `cmp` identical.
- AC5 Looks right — proven by: write a throwaway swatch PNG of both palettes to /tmp (not committed) and view it. Report in one line whether pop stands out against meadow.
- AC6 Green — `npm run check && npm test && npm run build` → exit 0.

## Tests
`tools/art/tests/test_palette.py`: AC1, AC2, AC3. These guard broken palette edits and wrongly ordered ramps, which would silently invert shading in ART-003.
