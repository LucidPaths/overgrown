# 01 — Tech & Multiplayer

## Goals and constraints

- **Instant load from a link**, including inside X's in-app browser on phones. That is the viral path (see the Tweetcraft precedent). X Player Cards forbid games inline in posts, so we are a link that opens a page, not an embed. That makes first-load size and time the top technical metric.
- **Phones are first-class.** Touch input, mid-range mobile GPUs, and battery cost all matter.
- **No mandatory backend for solo play.** Multiplayer needs only a tiny signaling service.
- **Every asset is generated by code** at build time (or at runtime, where cheap).

## Stack

| Layer | Choice | Why |
|-------|--------|-----|
| Language | TypeScript (strict) | One language for client, sim and the tiny services |
| Rendering | PixiJS (WebGL, WebGPU when available) | Fast batched 2D sprites; a small fraction of a full engine's web export |
| Build | Vite | Fast dev loop, code splitting |
| Simulation | Plain TS, in a Web Worker | Keeps the render thread smooth; the worker is the "server" when hosting |
| Netcode | WebRTC DataChannels, peer-to-peer | Host-in-tab; no game servers |
| Signaling | Small WebSocket service (self-hostable; ours runs on Hetzner) | Peers find each other; no game traffic passes through it |
| Storage | IndexedDB (worlds, characters), export/import as files | Valheim-style local ownership |
| Assets | Python 3 pipeline (Pillow, NumPy) producing atlases + JSON | Deterministic, code-generated art and audio |
| Auth | Sign in with X (OAuth 2.0 PKCE) | Identity label for characters (→ OQ-004 for cost and verification) |

## Architecture

```
client (main thread)            sim worker                    peers
 ├─ input (kb/mouse/touch) ──▶  ├─ world state (chunks)  ◀──▶ WebRTC
 ├─ renderer (Pixi)       ◀──   ├─ entity systems (ECS)
 ├─ UI                          ├─ sim LOD scheduler
 └─ audio (WebAudio)            └─ save/load (IndexedDB)
```

- The simulation is an ECS-style data layout (typed arrays), so thousands of coarse entities stay cheap.
- The renderer only reads snapshots from the sim. It never mutates game state.

## Multiplayer model

- **Solo is just a world with one player.** The same code path runs either way.
- **Open to friends** generates a share link. The host's tab registers with the signaling service, and joiners connect directly over WebRTC.
- **Split-by-area authority** (Valheim-style zone ownership): each chunk region is simulated by one peer, normally the player nearest to it. Ownership transfers as players move. The world host owns persistence and anything nobody is near.
- **Trust model: Valheim-style.** Characters are local files and cheating is possible. We accept this and don't build anti-cheat. Worlds can kick and ban.
- **Player cap: 10 per world.**
- **The world only exists while someone hosts it.** When the host leaves, the world closes. Host migration is an open question (→ OQ-005).

## Persistence

- **World save:** seed + diffs from generated state + full sim state of visited regions, in IndexedDB. Exportable as a file.
- **Character save:** local, exportable, tagged with the X identity that created it. Valheim-style: it carries inventory between worlds.
- **Corpses live in the world save**, not the character save.

## Performance budgets (starting targets, to be measured)

- First playable frame in **≤ 3 s** on a mid-range phone over 4G. Initial download target **≤ 5 MB**, with assets streamed after that (→ TEC-012).
- **60 fps** desktop, **≥ 30 fps** mid-range phone, with ~300 on-screen entities.
- Full simulation within ~2 screens of each player. Coarse simulation beyond that, ticked at ≤ 1 Hz per region.
