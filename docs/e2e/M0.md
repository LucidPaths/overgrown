## Additional checks

### Same seed → same first frames; different seed → different layout

- **Method:** screenshots at the same short delay are *not* reliable for pixel comparison: the sim starts from a wall-clock timer in the worker, so a screenshot at "500 ms" lands on a different tick each load (movers have moved). Instead I compared the snapshot data **tick by tick** (hash of the x/y buffers), which is exactly what the first frames are drawn from.
- Same seed across reloads: `?seed=1` run vs another `?seed=1` run: **26/26 ticks identical**; no `?seed` vs `?seed=1`: **26/26 identical** (default is 1).
- Different seed: seed 1 vs 2, vs 4294967295, vs 12345: **0/26 identical** each. Pixel diff of 640×360 screenshots seed 1 vs seed 2: 24.0 % of pixels differ (`04-seed1-640x360.png`, `04-seed2-640x360.png`), movers visibly in different places.
- Invalid seeds (`abc`, `-1`, `1.5`, `4294967296`): fall back to seed 1 with a clear `console.warn` ("ignoring invalid ?seed=… using 1"), no errors; `?seed=abc` matched seed 1 for 26/26 ticks.

Time to first canvas, local (SwiftShader, no network limits, cold cache, 5 runs): canvas in DOM **184–218 ms**; first snapshot received 489–556 ms; **first painted frame with sprites 511–582 ms**; DOMContentLoaded 110–139 ms.

Simulated mobile (CDP: 1.6 Mbit/s down, 150 ms RTT, CPU 4× slower; 3 runs, cold): canvas in DOM 1.78–1.92 s; **first painted frame with sprites 2.65–2.79 s**. That is under 3 s but only by about 0.2–0.35 s. **Local ≠ real mobile 4G**: this is an emulation on a desktop CPU, not a mid-range phone, and the headless profile does not model TLS setup, in-app browser overhead or low-end GPU init. Treat the margin as thin.

Why it is slow-ish under latency: the load is a serial waterfall: `index.html` → `index.js` → 13 Pixi chunks (fan-out) → `core.json` → `core.png` → **only then** `sim-worker.js` (the worker is created after the atlas finishes). At 150 ms RTT each step costs a round trip.

## Risks seen

1. **First-frame margin is thin under emulated mobile (2.65–2.79 s vs 3 s)** with a trivial scene. M1 adds world data and more atlases; the serial waterfall (13-chunk fan-out, sim worker only started after the atlas) will eat the margin quickly. TEC-016 (CI load check) only guards bytes, not time or round trips.
2. **Render resolution is uncapped DPR.** A DPR-3 phone gets a 1170×2532 backing store. Likely fill-rate trouble on mid-range GPUs at M1+ scale. Unverified on real hardware.
3. **Sim worker starts late and uses `setInterval`** at TICK_MS/2: fine here (max snapshot gap 66.7 ms desktop, 98 ms on the phone profile), but background-tab throttling of timers was not tested and will slow the sim in a hidden tab.
4. **Build prerequisites and commands live only in `CLAUDE.md`**; `README.md` has none.
5. **`sim` has no build/run entry for Node** (TS source exports only). Fine now; the dedicated host will need a documented run path.
6. **Debug movers are scaffolding** (`debug-movers.ts`, `debug/*` frames), as noted in CLAUDE.md traps; the atlas has just 2 frames, so atlas packing at realistic sizes is untested.
7. SwiftShader `GPU stall due to ReadPixels` warnings: harmless in this environment, source (Pixi vs driver) not pinned down.
